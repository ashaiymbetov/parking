## D-001. Стек
**Статус:** предложено
**Контекст:** нужен backend на Python/Go/Node, React/Vue, PostgreSQL.
**Решение:** NestJS + TypeORM, React + Vite, PostgreSQL 16, Docker Compose.
**Почему:** я выбрал node js, т.к. это мой основной стек на работе.

## D-001a. Фоновые задачи через опрос PostgreSQL, без Redis/BullMQ
**Статус:** предложено
**Контекст:** нужно снимать брони и слать напоминания в заданный момент, переживая перезапуск.
**Варианты:** (а) таймеры в памяти; (б) BullMQ + Redis; (в) pg-boss; (г) свой воркер: опрос таблиц с `FOR UPDATE SKIP LOCKED`.
**Решение:** (г).
**Почему:** состояние уже в PostgreSQL, лишний сервис не нужен; задачи выводятся из данных (бронь сама знает свой срок), поэтому нечего синхронизировать между БД и очередью; SKIP LOCKED позволяет запускать несколько воркеров без дублей.

## D-002. Защита от пересечения броней на уровне БД
**Статус:** предложено
**Контекст:** «Две брони на одно место не пересекаются, даже если оформлены одновременно». Проверка в коде (SELECT, затем INSERT) подвержена гонке.
**Варианты:** (а) проверка в коде; (б) SERIALIZABLE-транзакции с повторами; (в) `EXCLUDE USING gist` с `tstzrange`.
**Решение:** (в).
**Почему:** инвариант гарантирует сама БД при любой конкуренции, код проще, конфликт превращается в понятную ошибку 409.

## D-003. Тарификация: границы, округление, бесплатный период (Q1, Q2, Q3)
**Статус:** принято
**Контекст:** «Тариф по минутам, дневной и ночной… визит через границу считается правильно, копейки не теряются». Нужно определить, что такое минута на границе.
**Варианты:** (а) минута по тарифу момента её начала, длительность округляется вверх; (б) посекундный расчёт с одним округлением итога; (в) минуты по календарным минутам стены.
**Решение:** (а). День 07:00–23:00, ночь 23:00–07:00 в TZ парковки (`PARKING_TZ`, по умолчанию `Asia/Bishkek`). Минуты отсчитываются от момента заезда. Бесплатного периода нет.
**Почему:** буквально соответствует «тарифу по минутам»; всё в целых копейках без делений; легко проверить поминутным перебором в property-тестах. Вариант (в) даёт неинтуитивное: визит в 61 секунду может стоить 3 минуты.

## D-004. Заезд по брони: окно, место, пересидевший (Q5, Q6, Q7)
**Статус:** принято
**Контекст:** нужно связать событие шлагбаума «номер X заехал» с бронью.
**Решение:** заезд номера с бронью `confirmed` в окне `[start − EARLY_ENTRY_MIN, start + NO_SHOW_GRACE_MIN)` (по умолчанию ±15 мин) привязывается к ней, бронь → `checked_in`, машина ставится на забронированное место. Раньше окна — обычный заезд без брони (бронь затем станет no-show). Если забронированное место физически занято пересидевшим — выдаётся другое свободное место, бронь всё равно `checked_in`, пишется аномалия `booked_spot_occupied`; если свободных нет — 409 `NO_FREE_SPOT`, бронь остаётся `confirmed`.
**Почему:** правило зависит только от времени и номера, детерминировано и проверяемо; водитель с бронью не теряет право на парковку из-за чужого опоздания.

## D-005. Вход, роли, гости, владение номером (Q8, Q9)
**Статус:** принято
**Решение:** email + пароль, JWT. Роли: `driver` (профиль, машины, брони, свои визиты и счета) и `operator` (симулятор шлагбаума, все визиты, аномалии). Машина без профиля может заехать: визит и счёт создаются без владельца (гость). Нормализованный номер принадлежит максимум одному профилю (`cars.plate UNIQUE`).
**Почему:** простая и привычная модель; гости нужны, потому что шлагбаум не знает, кто зарегистрирован. Уникальность номера исключает неоднозначность «чей визит».

## D-006. No-show: оплата, снятие после простоя, машина уже внутри (Q4, Q11)
**Статус:** принято
**Решение:** за бронь, на которую не приехали, денег не берём — оплата только по факту визита. Снятие выполняет worker при `now ≥ start + NO_SHOW_GRACE_MIN`; если момент пришёлся на простой — снимается на первом тике после старта, письмо и событие отправляются. Если машина к началу брони уже внутри как заезд без брони (заехала раньше окна), бронь к визиту не привязывается и становится no-show; визит оплачивается по факту.
**Почему:** задачи выводятся из данных, а не из таймеров — перезапуск ничего не теряет. Правило про «уже внутри» простое и не требует перепривязки визитов.

## D-007. Напоминание за 10 минут до конца брони (Q10)
**Статус:** принято
**Решение:** напоминание создаётся для броней в статусах `confirmed` и `checked_in` строкой `email_outbox` с `UNIQUE (booking_id, kind)`. Если срок напоминания прошёл во время простоя, но бронь ещё не закончилась — шлём; если закончилась — строка со статусом `skipped` и аномалия `reminder_missed`. Создание письма — ровно одно; доставка — at-least-once: при падении между ответом SMTP и COMMIT письмо может уйти повторно (`Message-ID` детерминирован от id строки outbox).
**Почему:** «одно письмо» гарантирует БД, а не код. Exactly-once доставку по SMTP без двухфазного протокола обеспечить нельзя — фиксируем честно.

## D-008. Ограничения на бронь (Q12)
**Статус:** принято
**Решение:** длительность от 15 минут до 24 часов, начало не раньше «сейчас» и не дальше 7 дней вперёд. Границы кратны минуте (DTO + `CHECK` в БД). Бронь с началом в ближайшие 15 минут на место, где сейчас открытый визит, отклоняется 409 `SPOT_OCCUPIED` (проверка под `FOR UPDATE` строки места).
**Почему:** минимум 15 минут исключает брони короче окна напоминания; кратность минуте упрощает тарификацию и отображение; запрет брони «на сейчас» на занятое место убирает заведомо невыполнимые брони.

## D-009. Одна машина не держит две пересекающиеся брони
**Статус:** принято
**Решение:** второе ограничение `EXCLUDE USING gist (car_id WITH =, period WITH &&) WHERE (status IN ('confirmed','checked_in'))`, ошибка 409 `CAR_ALREADY_BOOKED`.
**Почему:** иначе заезд по номеру неоднозначен (к какой брони привязывать). Защищено БД, как и основной инвариант.

## D-010. Выбор места для заезда без брони
**Статус:** принято
**Решение:** свободное для walk-in место — активное, без открытого визита и без брони `confirmed`, пересекающей `[now, now + 15 мин)`. Из свободных выбирается место с самым поздним следующим началом брони (или без броней), затем по коду. Кандидаты берутся `FOR UPDATE SKIP LOCKED`, страховка — частичный уникальный индекс на открытый визит по месту.
**Почему:** место не отдаётся тому, кто вот-вот приедет по брони; выбор «самого свободного в будущем» уменьшает конфликты пересидевших (D-004).

## D-011. Состояние мест и realtime
**Статус:** принято
**Решение:** состояние места производное (`occupied` > `booked` > `free`), считается одной SQL-функцией. Последнее разосланное состояние хранится в `spot_state` с монотонным `version`. Мутации API и тики worker'а обновляют `spot_state` только при реальном изменении и в той же транзакции вызывают `pg_notify`; API слушает `LISTEN` и шлёт в socket.io. Клиент игнорирует события со старой `version` и перезапрашивает схему при переподключении.
**Почему:** состояние меняется и по времени (без запросов) — снапшот позволяет worker'у разослать именно изменения; NOTIFY доставляется только после COMMIT; не нужен Redis.

## D-012. Идемпотентность шлагбаума и журнал аномалий
**Статус:** принято
**Решение:** каждое обращение к шлагбауму пишется в `gate_events`. Запросы симулятора несут `Idempotency-Key`; повтор с тем же ключом возвращает сохранённый ответ без повторной обработки. Аномалии (выезд без заезда, двойной заезд, нет мест, мусорный номер, занятое забронированное место, пропущенное напоминание) — в отдельной таблице `anomalies`.
**Почему:** ключ отличает сетевой ретрай датчика от настоящего двойного заезда. Аномалии создаёт не только шлагбаум, но и worker — отдельная таблица удобнее для оператора.

## D-013. Оплата эмулируется
**Статус:** принято
**Решение:** счёт создаётся при выезде в той же транзакции, что и закрытие визита, и считается оплаченным на терминале шлагбаума. Платёжного шлюза нет.
**Почему:** задание требует итоговый счёт и историю, но не приём платежей; заглушка внешних сервисов разрешена.

## D-014. Версии тарифа по периоду действия
**Статус:** принято
**Решение:** таблица `tariffs` с `valid_during tstzrange` и `EXCLUDE USING gist (valid_during WITH &&)`. Минута тарифицируется по версии, действующей в момент её начала. Начальная версия — из миграции/сида.
**Почему:** «тариф, действующий в это время» — смена цен не должна менять уже идущие и закрытые визиты задним числом.

## D-015. Управляемое время для E2E и демо
**Статус:** принято
**Решение:** `Clock`-провайдер в двух реализациях: системная и управляемая. При `CLOCK_MODE=controllable` регистрируется `POST /api/test/clock` (установить/сдвинуть время); в обычном режиме маршрута нет. Worker и API в демо-режиме читают общее смещение времени из БД.
**Почему:** E2E-проверка no-show и напоминаний без ожидания реальных 15 минут; короткие пороги через env остаются вторым способом демо.

## D-017. NestJS 11, а не 12
**Статус:** принято
**Контекст:** актуальный Nest CLI 12 генерирует проект на ESM с Vitest и oxlint; в стеке проекта — Jest. Пакеты линии 12 (`@nestjs/config` 12, `@nestjs/typeorm` 12) поставляются только как ESM, Jest на Node 22 их не загружает.
**Варианты:** (а) Nest 12 + перевод тестов на Vitest (смена стека); (б) Nest 12 + ручная перенастройка Jest под ESM; (в) Nest 11 (CommonJS + Jest из коробки).
**Решение:** (в). NestJS 11.x, `@nestjs/config` 4.x, `@nestjs/typeorm` 11.x, TypeORM 1.x.
**Почему:** линия 11 поддерживается (11.2.7 вышла одновременно с 12.1.2), генератор даёт ровно стек из CLAUDE.md, без экспериментальных флагов Jest. Переход на 12 возможен позже отдельным решением.

## D-019. Миграции: явный список, применяет API
**Статус:** принято
**Решение:** миграции перечислены явно в `src/database/migrations/index.ts` (без glob). Backend запускается с `migrationsRun: true`; worker — с `false` и стартует в compose только после того, как backend прошёл healthcheck. `synchronize: false` везде, это проверяет юнит-тест. Первая миграция только включает `btree_gist` и `citext`.
**Почему:** glob по `.ts/.js` по-разному ведёт себя в ts-jest, ts-node и `dist`; явный список работает одинаково. Одна точка применения миграций исключает гонку двух процессов при старте. Ограничение: при нескольких репликах API миграции надо будет выносить в отдельный шаг (сейчас реплика одна).

## D-020. Тестовая БД
**Статус:** принято

## D-021. Сид: справочники — миграцией, демо-пользователи — скриптом
**Статус:** принято
**Контекст:** нужны 20 мест, тариф и тестовые пользователи.
**Варианты:** (а) всё в миграциях; (б) справочники в миграции, пользователи — отдельный сид; (в) всё в сид-скрипте.
**Решение:** (б). Миграция `SeedReferenceData` создаёт 20 мест (A01–A10, B01–B10) со строками `spot_state` и тариф. Демо-учётки (`operator@`, `driver1@`, `driver2@parking.local`, пароль `parking123`, машины `A123BC`, `B777OP`, `E001KX`) создаёт идемпотентный `seedDemoData`: при старте API, если `SEED_DEMO=true` (в compose включено), и командой `npm run seed`.
**Почему:** без мест и тарифа система не работает — они должны быть везде, включая тестовую БД. Учётки с известным паролем — только для демо, в схему и в тестовую БД не попадают.

## D-022. Хэширование паролей — scrypt из node:crypto
**Статус:** принято
**Варианты:** scrypt (встроен), argon2 (нативный модуль), bcryptjs (медленнее, лимит 72 байта).
**Решение:** scrypt с параметрами OWASP: N=2^17, r=8, p=1, соль 16 байт, ключ 64 байта. Формат `scrypt$N$r$p$salt$key` (base64), сравнение `timingSafeEqual`, битый хэш = несовпадение.
**Почему:** без новых зависимостей и нативной сборки; параметры хранятся в хэше — их можно усилить позже без миграции паролей. Цена — ~128 МиБ памяти и сотни миллисекунд на один хэш: на демо-нагрузке приемлемо.

## D-023. Соглашения схемы
**Статус:** принято
**Решение:** статусы и виды — `text` + `CHECK (… IN (…))`, а не типы ENUM PostgreSQL; все ограничения и уникальные индексы именованы; деньги — `integer` копеек; кратность брони минуте проверяется через `mod(extract(epoch FROM …), 60) = 0`.
**Почему:** CHECK меняется одной миграцией без `ALTER TYPE`; имена позволяют тестам проверять, что сработало именно нужное ограничение, а API — переводить нарушение в понятную ошибку; `date_trunc` для `timestamptz` зависит от `TimeZone` сессии, epoch — нет. Урок этапа: `CHECK (x IN (…))` пропускает `NULL` — для nullable-колонок нужен явный `IS NOT NULL`.

## D-024. Конкурентные вставки в EXCLUDE: 23P01 или 40P01
**Статус:** принято
**Контекст:** тест «10 параллельных броней на одно место» показал: ровно одна бронь проходит всегда, но проигравшие транзакции PostgreSQL иногда отклоняет как `40P01 deadlock_detected`, а не `23P01 exclusion_violation` (в эксперименте — 4 раунда из 20). Каждая транзакция сначала вставляет свою строку, потом ждёт чужие незакоммиченные.
**Решение:** сервис броней трактует и `23P01`, и `40P01` при вставке брони как конфликт (409 `BOOKING_CONFLICT`); тест принимает оба кода, но требует ровно одну успешную вставку и одну строку в БД.
**Почему:** инвариант не нарушается; меняется только код ошибки. Повтор после `40P01` дал бы тот же итог (`23P01`), поэтому сразу отвечаем конфликтом.

## D-025. Тарификация: контракт и поведение на краях
**Статус:** принято
**Контекст:** правила D-003 и D-014 нужно реализовать как чистую функцию (CLAUDE.md, принцип 9).
**Решение:**
- `calculateCharge({ enteredAt, exitedAt, tariffs, timeZone })` в `src/tariffing/`, без NestJS, БД и импортов из остального приложения (правило ESLint `no-restricted-imports`). Время — абсолютные `Date` (UTC), локальное время — только внутри, через Luxon.
- Часовой пояс берётся из входа (`PARKING_TZ`), а не из `tariffs.timezone`; при загрузке тарифов из БД сервис должен проверить, что они совпадают.
- Сегмент результата — серия целых минут с одной ценой (версия + день/ночь); `from`/`to` — границы этих минут, сегменты покрывают оплаченный интервал без зазоров.
- Ошибка `TariffingError` (а не счёт) при: невалидной дате, выезде раньше заезда, неизвестном часовом поясе, минуте без действующей версии тарифа, битом или пересекающемся тарифе. Бесплатных «дыр» в тарифе не бывает: это ошибка конфигурации.
- Переход на летнее/зимнее время: минуты — реальное прошедшее время (ночь весной короче на час, осенью длиннее); граница дня/ночи — по локальным часам. Если граница попадает в пропущенный или повторяющийся час (для 07:00/23:00 такого не бывает), цена меняется в момент перевода часов и при каждом прохождении часов через границу.
- Зависимости: `luxon` (+ `@types/luxon`) — часовые пояса и DST (стек); `fast-check` (dev) — property-based тесты (стек).
**Почему:** счёт — деньги; на некорректных данных лучше явная ошибка, чем тихо неверная сумма. Правило «цена по локальным часам» единое для всех случаев и проверяется эталоном «поминутный перебор».

## D-026. Вход, профиль, бронирование: детали API
**Статус:** принято (подтверждено перед этапом 5)
**Решение:**
1. Отмена брони — только `confirmed` и только до её начала; после начала бронь сама станет no-show (денег за неё нет, D-006).
2. «Начало не раньше сейчас» (D-008) = не раньше начала текущей минуты: из-за кратности минуте иначе нельзя забронировать «на сейчас». «Не дальше 7 дней» — для начала брони.
3. Машину можно удалить, только если у неё нет ни одной брони и ни одного визита (409 `CAR_HAS_HISTORY`): история на неё ссылается. Мягкое удаление — отдельным шагом при необходимости.
4. Один access-токен JWT на 12 ч (`JWT_TTL_SECONDS`), без refresh. Регистрация создаёт только водителя; оператор — из сида.
5. Неизвестный email и неверный пароль — один ответ 401 `INVALID_CREDENTIALS`, время ответа выравнивается проверкой против фиктивного хэша.
6. Ошибки API — всегда `{code, message}` (+ поля вроде `reason`, `details`); ошибки валидации DTO — 422 `VALIDATION_FAILED`. `/health` сохраняет собственный формат 200/503.
7. Нормализация номера отвергает всё, кроме латиницы, цифр, кириллических двойников, пробелов и дефисов (например, `ß` → `SS` при upper-case не принимается): лучше 422, чем угаданный номер.
8. Доступ к БД — параметризованный SQL через TypeORM `DataSource`/`EntityManager`, без entity-классов: `tstzrange` и EXCLUDE ORM не поддерживает, а запросы короткие и проверяются e2e-тестами на реальной БД.
**Зависимости:** `@nestjs/jwt` 11 (CommonJS, совместим с Nest 11) — подпись и проверка токенов; passport не нужен для одного Bearer-сценария.
